# Results and datasets — final_exp

**Generated:** 2026-11-22  
**Scope:** every experiment in `final_exp/`, the dataset/trace used for each one, and a
short description of every dataset.  The numerical results below are the outputs of
`experiments/run_all.py` (full run: N=40, T=8000, 10 seeds) and are stored in

## 1. Quick answer: what was run on what

* **Most experiments (01-04, 08-12, 14-15, 17)** use a **synthetic Zipf/Poisson world**
  (`sim.trace.synthetic_world`): 40 services, 8 000 requests, Zipf `rho=1.2`, Poisson rate
  0.5 req/ms, 10 seeds.  This is the only way to run the parameter sweeps (theta, U/D, C,
  cap_mult, Zipf rho, request rate).
* **exp05 and exp13 family 1** use the **adversarial Large Sequence** from the proof of
  Theorem 1 (`sim.trace.large_sequence`), not a random trace.
* **exp10 and exp13 family 2** use small **synthetic Zipf** traces with the exact MILP
  optimum.
* **exp06** is analytic (ski-rental), **exp07** is random projection instances.
* **exp16 is the only experiment on real data**: the bundled **Google cluster traces 2011**
  CSVs (`data/google.csv`, `data/google_dataset2_30.csv`, `data/google_dataset2_paper.csv`,
  `data/google_dataset2.csv`).
* **SHARCNet** (the paper's second real dataset) is **not bundled and not reachable** from
  this codespace; it is documented as an open item, not replaced by synthetic data.

## 2. Datasets used by the experiments

### 2.1 Real traces: Google cluster traces 2011

Source: `clusterdata-2011-2` (`task_events`), prepared by `final_exp/data/prepare_google.py` with the paper's recipe:

* keep only `SUBMIT` events (event type 0);
* one request per `(JobID, distinct Timestamp)`;
* a service's CPU/RAM/disk is the max over the tasks of that job (first occurrence in the loader);
* zeros/missing CPU/RAM/disk are replaced by the column median;
* timestamps are converted from microseconds to milliseconds;
* the loader treats the disk column as **KB** and converts it to MB (`disk_unit_mb=1/1024`).

Notes on the real traces:

* `google.csv` is the largest bundled trace: 50 000 requests over 4 619 services (about 70 minutes of trace time).  It is the only file large enough for the 50-slot capacity used in exp16.  It contains 33 rows with blank CPU/RAM/disk fields; the loader replaces those by the column median, exactly as the paper's recipe does.
* `google_dataset2_30.csv` is the paper-like `dataset2`: 1 000 requests, 30 unique services.  The services are mostly grouped together, as the paper notes.
* `google_dataset2_paper.csv` and `google_dataset2.csv` are both 1 000-row slices with **6** unique services (despite the `_paper` name in the first file).  The 30-service version is the closer match to the paper's `dataset2` description.
* With the paper-style bandwidth parameters in `sim/catalog.py`, `M_n < l_n` for every service in these traces.  Therefore the `theta=1` (Online-DRL) and `theta=0` (LL-RC) triggers fire on the same requests, and Online-DRL and LL-RC coincide in exp16.  The paper's exact latency/cost split needs its exact bandwidth/`l_n` parameters, which are not recoverable from the damaged PDF.

### 2.2 Synthetic Zipf/Poisson world

Generated by `sim.trace.synthetic_world` (no CSV).  Default full-run parameters:

| property | value |
|---|---|
| catalogue size `N` | 40 services (exp10/13 use 10-16; exp14 sweeps 20-320) |
| trace length `T` | 8 000 requests (exp09/17 use the same default; exp13 family 2 uses 1 200) |
| popularity | Zipf with exponent `rho = 1.2` (exp17 sweeps 1.0-2.0) |
| arrivals | Poisson, rate 0.5 requests/ms (exp17 sweeps 0.25-2.0) |
| raw demands | CPU `lognormal(0, 0.6)`, RAM `lognormal(1, 0.6)`, disk `lognormal(3.5, 0.8)` |
| capacity | `max(8 * mean_demand, max_demand)` per resource by default; `cap_mult` varies in exp04/08/11/12 |
| bandwidth | `U = 100` Mbps uplink, `D = 1000` Mbps downlink, `rtt = 20` ms, request `100` kbit |
| seeds | 10 by default (3 in `--quick`) |

Some experiments add an **imbalance** factor: one random resource of each service is multiplied by 3-4, which makes slot reductions wasteful.  The synthetic world is the only data source for the sensitivity sweeps (theta, bandwidth, capacity, Zipf rho, request rate) because the real trace has only one fixed resource vector per service.

### 2.3 Adversarial Large Sequence (Theorem 1)

Generated by `sim.trace.large_sequence` from the proof of Theorem 1 in the paper.  It is not a random dataset; it is a constructed request sequence (BS1, BS2, BS3, MS repeated `n_reps = 2k` times) whose offline optimum is known exactly:

* `k` = cache capacity, tested at `k = 3, 6, ..., 24`;
* `M = 6`, `Ml = 12`, `l = 1`, burst fraction 0.5;
* `OPT = (k + 2n) l` (paper eq. 17);
* each `k/3` block is disk-heavy, RAM-heavy, or CPU-heavy, and the MS block needs the large demand of every resource, forcing a full-cache eviction.

Used by exp05 and by family 1 of exp13.  It is the only dataset that tests the competitive-ratio scaling with `k` in the adversarial sense.

### 2.4 Analytic / random inputs

* **exp06 (ski rental)**: no dataset; analytic minimax ratio and a Monte-Carlo check of the randomized threshold.
* **exp07 (projection)**: 60 random instances (10 in `--quick`) with `N` drawn uniformly from 10-80 and random demands `a ~ U(0.01, 0.6)`, compared against the exact QP.
* **exp14 (time complexity)**: synthetic worlds with `N = 20, 40, 80, 160, 320` or `C = 4, 8, 16, 32, 64`; three repeats per point.

## 3. Full results output (all 17 experiments)

Generated by `experiments/summarize.py` from `results/*.json`.  The simulator, the 17 experiments and the exact conditions are described in the top-level `README.md`.
